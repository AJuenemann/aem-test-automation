# Code-Review: lokale Test-Web-UI (`webui/`)

Was diese Komponente macht: Ein kleiner localhost-Node-Service startet Playwright als Child-Prozess, streamt Logs per SSE, persistiert pro Lauf einen JSON-Report und zeigt Ergebnisse, Historie und Baseline-Vergleiche in einer Vanilla-JS-Oberfläche. Bewusst einfach: nur Node-Bordmittel, kein Auth, kein Build-Step, genau ein aktiver Lauf.

Angenommene Last: eine Person, lokal, ein Lauf zur Zeit. Dagegen bewerte ich.

Die Sicherheitsgrundlagen sitzen: Playwright wird mit `spawn`/`execFile` und Array-Argumenten gestartet, nie über eine Shell — klassisches Command-Injection ist damit ausgeschlossen. Pfad-Traversal ist an allen vier statischen Routen über `serveFileWithin` abgefangen. Credentials gehen nicht durch die UI; die Befehls-Vorschau zeigt nur `baseUrl`/`env`.

Watch for: Der Abbruch-Status wird beim Prozessende überschrieben (ein abgebrochener Lauf erscheint als "fehlgeschlagen") — confirmed. Das Backlog-Log wächst unbegrenzt bei langen Läufen — confirmed, unter der erklärten Last unkritisch. UI-Mode terminiert den Service-Zustand nie sauber — likely.

**Verdict**: NEEDS_CHANGES

## High-level view

Der Prozesslebenszyklus hat eine Lücke: `child.on('close')` setzt den Status hart auf `passed`/`failed` und überschreibt damit das vorher gesetzte `cancelled`. Ein vom Nutzer abgebrochener Lauf landet als Fehlschlag in Historie und Statuszeile.

Die Spawn-Sicherheit ist korrekt gelöst (Array-Argumente, keine Shell). Was offen bleibt, ist kein Injection-Risiko, sondern Argument-Confusion: `grep` und ausgewählte Dateipfade gehen ungeprüft als CLI-Argumente an Playwright. Da alle Pfade aus dem servereigenen Katalog stammen und der Dienst nur lokal läuft, ist das praktisch harmlos, aber eine `grep`-Eingabe wird als Regex interpretiert und kann bei ungültigem Muster den Lauf ohne klare Meldung scheitern lassen.

Das XSS-Modell im Frontend ist konsistent: Report-Titel, Fehlertexte und Historien-Felder laufen entweder durch `escapeHtml` oder durch `textContent`. Das hält, solange die Konvention bei künftigen Erweiterungen durchgehalten wird.

Zwei Zustandsfallen bleiben: Der UI-Mode startet einen Langläufer-Prozess, der nie ein `done` liefert, das zuverlässig den UI-Zustand zurücksetzt; und das Log-Backlog puffert den gesamten Lauf im Speicher. Beides ist unter Einzelnutzung lokal tolerierbar, aber benannt.

<details>
<summary>Issues (7)</summary>

1. **Abbruch-Status geht verloren** — `child.on('close')` überschreibt `cancelled` mit `passed`/`failed`. Vor dem Überschreiben prüfen, ob der Status bereits `cancelled` ist.
2. **`grep` ist ein ungeprüftes Regex** — ungültiges Muster lässt den Lauf ohne verständliche Meldung scheitern. Muster serverseitig mit `new RegExp` validieren und bei Fehler 400 zurückgeben.
3. **UI-Mode hinterlässt hängenden Zustand** — der `--ui`-Prozess liefert kein sinnvolles `done`; `activeRun` bleibt belegt, Report fehlt. UI-Mode entweder als eigenen Pfad behandeln oder in dieser lokalen UI nicht anbieten.
4. **Log-Backlog wächst unbegrenzt** — `logBuffer` sammelt den gesamten Lauf im RAM. Für lange Suiten auf die letzten N KB begrenzen.
5. **`es.onerror` setzt keinen Status** — bei SSE-Abbruch werden nur die Buttons zurückgesetzt, die Statuszeile bleibt auf "läuft". Kurze Fehlermeldung setzen.
6. **`path.sep` in URL-Erzeugung** — `scanBaselines`/`toTestResultsUrl` splitten teils mit `path.sep`, obwohl der Pfad mit `/` gebaut wurde. Auf macOS/Linux folgenlos, auf Windows inkonsistent. Einheitlich mit `/` arbeiten.
7. **Fehlende Reports an Grenzen** — `/api/environments` und `loadReport` fangen Lesefehler nicht gezielt ab; greift nur der globale 500-Handler. Ausreichend, aber Meldung ist unspezifisch.

### Abbruch-Status wird beim Prozessende überschrieben

In `server.ts` setzt der Cancel-Handler den Status korrekt:

```ts
if (activeRun && activeRun.id === id && !activeRun.finished) {
  activeRun.meta.status = 'cancelled';
  activeRun.child.kill('SIGTERM');
```

Der `close`-Handler läuft danach und überschreibt bedingungslos:

```ts
child.on('close', async (code) => {
  run.finished = true;
  const status = code === 0 ? 'passed' : 'failed';
  run.meta.status = status;
```

Ein per SIGTERM beendeter Prozess liefert `code !== 0`, also wird jeder abgebrochene Lauf als `failed` in `meta.json` geschrieben und per `done`-Event gemeldet. Die Historie zeigt "fehlgeschlagen", obwohl der Nutzer bewusst abgebrochen hat. Auch das Frontend wertet `done` aus und setzt die Statuszeile auf "Lauf fehlgeschlagen", überschreibt damit das vorherige "Abbruch angefordert…".

Fix: im `close`-Handler den bereits gesetzten Abbruch respektieren.

```ts
const status = run.meta.status === 'cancelled'
  ? 'cancelled'
  : (code === 0 ? 'passed' : 'failed');
```

Im Frontend `done` entsprechend um einen `cancelled`-Zweig ergänzen, damit die Statuszeile stimmt.

### `grep` als ungeprüftes Regex

`runArgs.ts` reicht `grep` direkt durch:

```ts
if (req.grep && req.grep.trim() !== '') {
  args.push(`--grep=${req.grep.trim()}`);
}
```

Über `spawn` mit Array-Argumenten ist das **kein** Command-Injection — die Zeichenkette landet als ein Argument, nicht in einer Shell. Playwright interpretiert `--grep` aber als regulären Ausdruck. Eine Eingabe wie `Seite (anlegen` ist ein ungültiges Muster; Playwright bricht dann mit einem Regex-Fehler ab, den der Nutzer im Log nur schwer als Eingabefehler erkennt.

Fix an der Grenze, an der die Eingabe hereinkommt (`/api/run` bzw. `/api/preview`): Muster testweise mit `new RegExp(grep)` kompilieren und bei `SyntaxError` mit Status 400 und klarer Meldung antworten, statt den Lauf zu starten.

Ergänzend eine konzeptionelle Lücke derselben Kategorie: ausgewählte `files`/`tests` werden als positionale Argumente übergeben. Alle Werte stammen aus dem servereigenen Katalog, daher real unkritisch. Beginnt ein Spec-Dateiname jemals mit `-`, würde Playwright ihn als Option statt als Filter deuten. Ein `args.push('--')` vor den positionalen Filtern schließt das sauber ab.

### UI-Mode hinterlässt hängenden Zustand

`buildRun` setzt bei `uiMode` das Flag `--ui`:

```ts
if (req.uiMode) {
  args.push('--ui');
}
```

`--ui` startet Playwrights eigene, dauerhaft laufende Oberfläche. Der Child-Prozess endet erst, wenn der Nutzer dieses separate Fenster schließt. Bis dahin bleibt `activeRun` belegt, `finished` ist `false`, und ein weiterer Start wird mit "Es läuft bereits ein Test" abgelehnt. Es entsteht auch kein JSON-Report, der `close`-Handler fällt in den leeren `catch`, die Ergebnis-Tabelle bleibt leer. Zusätzlich wird `--reporter=list,json` in `startRun` angehängt, was mit `--ui` nicht zusammenpasst.

Das ist unter der erklärten "lokal, einfach"-Prämisse die aufwendigste Diskrepanz. Zwei schlanke Optionen: UI-Mode in dieser Runner-UI gar nicht anbieten (Playwrights UI-Mode ist ein eigenständiges Werkzeug, das man direkt per `npx playwright test --ui` startet), oder ihn als Spezialpfad behandeln, der den Child startet, sofort `done` meldet und `activeRun` freigibt, ohne auf Report/Streaming zu warten. Die erste Option löscht Code und passt besser zum Scope.

### Log-Backlog wächst unbegrenzt

```ts
const onData = (buf: Buffer) => {
  const text = buf.toString('utf-8');
  run.logBuffer.push(text);
  broadcast(run, 'log', text);
};
```

`logBuffer` hält den kompletten Lauf-Output im Speicher, damit spät verbundene SSE-Clients den Anfang sehen. Bei einem einzelnen Flow ist das vernachlässigbar; bei einer vollen, wiederholten Suite (`--repeat-each`) über viele Minuten summiert sich das. Unter Einzelnutzung lokal kein Ausfall, aber die einzige unbegrenzt wachsende Struktur im Prozess.

Fix, falls lange Läufe vorkommen: Backlog auf eine Obergrenze (z.B. letzte ~256 KB) begrenzen und beim Überlauf vorne abschneiden. `shortcut:`-tauglich — ein Kommentar, der die Grenze nennt, reicht, solange Läufe kurz bleiben.

### SSE-Fehler lässt Statuszeile stehen

Im Frontend:

```js
es.onerror = () => {
  $('#run').disabled = false;
  $('#cancel').disabled = true;
};
```

Reißt die SSE-Verbindung ab (Service weg, Netzwerk, Browser-Timeout), werden die Buttons zurückgesetzt, aber die Statuszeile bleibt auf "Lauf läuft…". Der Nutzer sieht einen scheinbar ewig laufenden Lauf. Eine Zeile `setStatus('failed', 'Verbindung zum Lauf verloren.')` schließt das. (Zu beachten: `onerror` feuert bei EventSource auch bei normalem `close`; prüfen, dass die Meldung nicht nach erfolgreichem `done` erscheint — `done` schließt die Quelle bereits, also `state.eventSource` als Wächter nutzen.)

### `path.sep` bei URL-Erzeugung

`toTestResultsUrl` und der `walk` in `scanBaselines` mischen Trennzeichen:

```ts
item.perEnv[env] = `/files/snapshots/${env}/${nextRel.split(path.sep).join('/')}`;
```

`nextRel` wird direkt darüber mit `/` zusammengesetzt (`rel ? `${rel}/${entry.name}` : entry.name`), nicht mit `path.sep`. Der `split(path.sep)` greift auf macOS/Linux also ins Leere (Trenner ist dort `/`, der String enthält `/`) und ist nur auf Windows überhaupt relevant — dort wäre er sogar nötig, würde aber am bereits mit `/` gebauten String fehlgehen. Rein kosmetisch bei aktueller Plattform, aber die Absicht ist unklar. Einheitlich mit `/` arbeiten und den `path.sep`-Split entfernen.

### Positive Muster

Pfad-Traversal ist konsequent über `serveFileWithin` zentralisiert; die `abs !== root && !abs.startsWith(root + path.sep)`-Prüfung ist korrekt und fängt auch den Fall "Pfad ist Präfix eines Geschwisterordners" ab. Der Shutdown ist idempotent und hat einen Notausstieg gegen hängende Keep-Alive-Verbindungen. `detectBlocker` trennt Umgebungs- von Funktionsfehlern sauber nach Projektkonvention. Das XSS-Modell im Frontend ist durchgehalten: dynamische Inhalte gehen durch `escapeHtml` oder `textContent`, die `innerHTML`-Nutzung beschränkt sich auf selbst kontrollierte Template-Strings mit escapten Einsetzungen.
